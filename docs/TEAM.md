# 四人团队分工与交付计划（V0.2 草案）

> 团队采用 Vibe Coding（AI 辅助编程）。成员 A/B/C/D 为待确认占位，不代表已指派实际人员。项目负责人暂由仓库负责人认领。

## 项目定位与现状
校园家教撮合平台，面向学生/家长和大学生家教，采用 uni-app + Vue 3 + TypeScript，共用 H5 与微信小程序代码。V0.1 仅有 Mock 家教展示与本地预约演示；尚无真实登录、数据库、资质认证、在线支付或订单通知。依赖安装、双端构建与交互仍待验证。

## 协作原则
1. 一人一主模块，跨模块改动先在 Issue 讨论；公共类型、路由、配置由 A 协调。
2. 所有任务先建 Issue，写清背景、范围、负责人、验收标准；每个 PR 对应 Issue。
3. AI 生成代码必须由提交人读懂并运行验证，不接受“AI 说能跑”作为验收。
4. 功能分支 feat/*、文档分支 docs/*；禁止直接向 main 提交未经评审的代码。至少一名非作者评审 PR。
5. 前后端先约定类型与接口，B 使用 Mock/适配层，C 不擅自修改 B 的页面。
6. 不提交 API Key、AppSecret、真实学生信息；V0.1 不宣称具备真实审核、支付或订单通知。
7. 每次合并更新 Issue 状态、测试结果与演示说明。

## 首轮任务（建议按依赖顺序执行）
- A：确认四名成员与截止日期；梳理用户故事、页面清单、演示路径；组织首次联调。
- B：检查现有页面，完成双角色导航和老师申请/资料页面原型。
- C：设计用户/家教/预约/审核数据模型与 API 契约；提出后端技术方案供团队确认。
- D：完成家长、大学生家教双侧访谈提纲与竞品分析模板；整理 H5/小程序测试用例。
- 全员：先验证 npm install、npm run build:h5、npm run build:mp-weixin；把环境问题记录为 Issue。

## 阶段里程碑（日期待团队确认）
M1 工程可运行与现有流程验收 → M2 双角色原型与状态演示 → M3 可选真实后端闭环 → M4 调研论证与路演演示。

## 评审和验收
- 日常异步：每人更新 Issue 的进展、阻塞、下一步。
- 每周集成：A 组织检查演示路径，B/C 联调，D 回归测试并记录问题。
- 任务完成定义：功能或文档可查看；提供验证步骤和结果；相关文档已更新；PR 经非作者评审并合并。
