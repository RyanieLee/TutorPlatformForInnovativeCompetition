# 四人协作与问题落地框架

## 目标
以“发现问题 → 拆解 Issue → 明确验收 → AI 辅助实现 → 交叉评审 → 合并演示 → 复盘”为闭环，每周交付可验证的产品增量。

## 角色与决策
- A（项目统筹/集成）：维护需求优先级、跨模块接口、主分支、版本演示和阻塞协调。
- B（前端）：页面、组件、UI、小程序/H5 适配。
- C（后端）：数据模型、API、鉴权和预约业务逻辑；后端技术选型需先评审。
- D（验证/商业）：用户调研、竞品、测试用例、缺陷复现、商业论证和路演。
- A/B/C/D 为待确认角色，不能视为真实成员已接受分配。
- 一项 Issue 只能有一位最终负责人；跨模块需求先由 A 协调，架构变更需要 B/C 共同确认。

## 问题拆解
1. **问题定义**：谁遇到什么问题？证据是什么？不解决有什么影响？
2. **期望结果**：用用户可观察的行为描述完成状态，而非“做个页面”。
3. **任务切片**：按垂直用户流程拆为预计 0.5–2 天的 Issue，写清依赖。
4. **优先级**：P0 阻断演示/安全；P1 核心闭环；P2 提升体验；P3 可选功能。
5. **验收条件**：列出可执行的步骤、预期结果和必要的双端检查。

## GitHub Issue 模板（复制使用）
```md
### 问题/背景
### 用户故事（作为…我希望…以便…）
### 本次范围 / 不做什么
### 交付物
### 验收标准（可测试）
- [ ] 
### 依赖 Issue / 风险
### 负责人 / 预计完成日期 / 优先级
### AI 使用说明与人工验证结果
```

## 工作流
Backlog（收集）→ Ready（定义明确）→ In Progress（开发）→ Review（交叉验收）→ Done（合并且可演示）。
- 每人最多同时 2 个 In Progress；超过 1 天阻塞，在 Issue 留言并通知 A。
- 开始任务前从 main 拉分支：feat/*、fix/*、docs/*；一个 PR 尽量只解决一个 Issue。
- AI 生成内容由提交人负责检查、运行和说明，不把 AI 自述当作测试。
- PR 包含关联 Issue、改动摘要、验证命令与结果、界面截图（如适用）、风险。
- 至少一名非作者评审；不得绕过评审直接提交功能到 main。
- 公共类型、路由、接口、配置修改前通知受影响成员。
- 不提交密钥或真实未成年人资料；演示数据必须标明为模拟。

## 每周节奏（建议）
- 周初 30 分钟：A 主持选定 4–8 个小 Issue，确认负责人、依赖和验收。
- 每日异步：各人在 Issue 更新“完成 / 下一步 / 阻塞”三项。
- 周中 20 分钟：B/C 对齐接口，A 解决依赖，D 提前准备测试。
- 周末 45 分钟：现场演示、交叉测试、关闭通过的 Issue，未完成任务重新评估。

## 完成定义（Definition of Done）
- [ ] 满足 Issue 验收标准
- [ ] 提交人实际运行并记录验证结果；涉及 H5/微信小程序则分别验证
- [ ] 失败和边界场景得到检查
- [ ] 相关文档与 Mock/真实功能状态同步
- [ ] 至少一位非作者完成评审
- [ ] 合并后主分支可演示

## 首轮执行顺序
1. A：运行 npm install、npm run build:h5、npm run build:mp-weixin；记录真实结果和阻塞，不预设成功。
2. A/B/C：确认 MVP 演示主线、页面与预约状态/API 契约。
3. B：完成双角色页面与空状态原型（优先 Mock）。
4. C：提交数据模型、API 契约、后端方案比较，选型批准后再开发。
5. D：完成两侧用户访谈提纲、竞品分析框架和关键流程测试用例。
6. 全员：首轮演示评审，按实际风险调整下一 Sprint。

## 待确认
赛事官方要求和截止日期；四名成员及时间投入；是否需要真实后端；部署预算。未确认前不承诺发布日期。
